# 이메일 인증 재발송 쿨다운 동시성 제어 — Redis SETNX 원자적 락 도입

## 배경

이메일 인증 코드 발송 API(`POST /api/v1/auth/email/send-code`)는 동일 이메일에 대해 재발송 쿨다운을 둬야 한다.
초기 구현은 Redis에서 쿨다운 키를 **조회(get) 후 없으면 설정(set)** 하는 2단계 구조였다.

```java
// 문제가 있던 방식 (get-then-set)
String existing = redisUtils.getValue(COOLDOWN_KEY_PREFIX + hash);
if (existing != null) {
    return false; // 이미 쿨다운 중
}
redisUtils.setValue(COOLDOWN_KEY_PREFIX + hash, "true", ttl); // 쿨다운 시작
```

## 문제: 레이스 컨디션으로 인한 중복 메일 발송

`get`과 `set`이 별개의 Redis 명령으로 분리되어 있어, 두 명령 사이에 다른 스레드/요청이 끼어들 수 있는 **경쟁 조건(race condition) 창**이 생긴다. 사용자가 "인증 메일이 안 왔다"며 버튼을 빠르게 연타하거나, 네트워크 재시도로 동일 요청이 겹치는 경우 이 창이 실제로 열린다.

- **검증 방법**: `CooldownAtomicLockBenchmarkTest` (`backend/src/test/java/com/study/studyproject/benchmark/`) — 동시 50개 요청을 20회 반복하며, get-then-set 방식의 성공(=메일 발송) 건수를 측정.
- **실측 결과**: 원자성이 없는 get-then-set 구현은 트라이얼마다 성공 건수가 들쭉날쭉했고, 평균적으로 1건이어야 할 성공이 다건으로 새는 것을 확인. 같은 시나리오를 JMeter로도 재현(`backend/loadtest/cooldown-lock-loadtest.jmx`, 50 threads 동시 실행) — 비원자적 구현에서는 동시 50개 요청 중 매번 여러 건이 200으로 통과해 중복 메일이 실제로 발송됐다.
- **원인**: `get`이 "비어있음"을 확인한 시점과 `set`이 실제로 키를 쓰는 시점 사이에 다른 요청들도 동일하게 "비어있음"을 보고 통과해버림 — check-then-act 패턴의 전형적인 동시성 버그.

## 해결: Redis SETNX 기반 원자적 락

`get` + `set` 두 명령을 Redis의 `SETNX`(`SET IF NOT EXISTS`) 단일 명령으로 교체했다. `SETNX`는 Redis 서버 내부에서 "키 존재 확인"과 "키 설정"을 **하나의 원자적 연산**으로 처리하므로, 두 연산 사이에 다른 요청이 끼어들 틈이 없다.

```java
// backend/src/main/java/com/study/studyproject/global/config/redis/RedisUtils.java
public boolean setIfAbsent(String key, String data, Duration duration) {
    ValueOperations<String, Object> values = redisTemplate.opsForValue();
    Boolean acquired = values.setIfAbsent(key, data, duration); // Redis SETNX + TTL
    return Boolean.TRUE.equals(acquired);
}
```

```java
// backend/src/main/java/com/study/studyproject/email/repository/EmailVerificationRepository.java
public boolean tryStartCooldown(String hash, Duration ttl) {
    return redisUtils.setIfAbsent(COOLDOWN_KEY_PREFIX + hash, "true", ttl);
}
```

`tryStartCooldown`의 반환값 자체가 "이번 요청이 락을 획득해 메일을 보낼 자격이 있는지"를 원자적으로 알려주므로, 호출부에서 별도의 조회 단계 없이 `true`일 때만 메일 발송을 진행하면 된다.

## 성과 / 검증

| 검증 방식 | 비원자적(get-then-set) | 원자적(SETNX) |
|---|---|---|
| 단위 테스트(`CooldownAtomicLockBenchmarkTest`, 동시 50요청 × 20트라이얼) | 평균 29.55건 통과 (중복 발송률 약 57%) | 매 트라이얼 정확히 1건 통과 (중복 발송률 0%) |
| JMeter 부하테스트(`cooldown-lock-loadtest.jmx`, 동시 50요청) | 통과 10건 | 통과 1건 |

- 두 방식 모두 "정상적으로는 1건만 통과해야 하는" 시나리오였고, 원자적 락 도입 이후 **모든 반복 실행에서 예외 없이 정확히 1건만 성공**하는 결정론적 동작을 확인했다.
- 표준편차 관점에서도 비원자적 구현은 트라이얼마다 성공 건수가 흔들렸지만(분산 큼), 원자적 구현은 분산 0(항상 동일)으로 수렴 — "운 좋게 테스트를 통과하는" 상태가 아니라 구조적으로 안전해졌음을 의미한다.

## 메일 발송을 비동기 처리한 이유

쿨다운 락(`tryStartCooldown`)으로 중복 요청 자체는 막았지만, 락을 획득한 **단 1건의 요청**이 실제로 메일을 보내는 과정도 설계가 필요했다. `EmailSender.send()`는 내부적으로 `JavaMailSender`를 통해 외부 SMTP 서버와 통신하는데, 이는 네트워크 I/O를 포함한 **블로킹(blocking) 호출**이다.

### 문제: 동기 호출 시 API 응답이 SMTP 통신 시간에 종속됨

`sendCode()`가 `emailSender.send(...)`를 동기적으로 호출하면, 컨트롤러 스레드는 SMTP 서버의 응답(연결, 인증, 전송 완료)까지 그대로 블로킹된다.

- SMTP 통신은 외부 네트워크 상태에 좌우되므로 지연이나 타임아웃이 발생하기 쉽고, 그 지연이 그대로 `POST /api/v1/auth/email/send-code` API의 응답 시간이 되어 버린다.
- Tomcat의 요청 처리 스레드 풀은 유한한데, 메일 발송이 느려지면(또는 외부 SMTP 장애로 멈추면) 해당 스레드가 오래 점유되어 **다른 API 요청까지 지연**시킬 수 있다 — 쿨다운 락으로 트래픽을 1건으로 줄여놔도, 그 1건이 스레드를 오래 붙잡는 문제는 별개로 남는다.
- 클라이언트 입장에서도 "인증번호 요청" 버튼을 눌렀을 때 사용자가 기다려야 하는 체감 시간이 메일 서버 응답 속도에 그대로 노출된다.

### 해결: `@Async` + 전용 스레드 풀로 분리

```java
// backend/src/main/java/com/study/studyproject/email/service/EmailSender.java
@Async("mailExecutor")
public void send(String email, String code) {
    SimpleMailMessage message = new SimpleMailMessage();
    message.setTo(email);
    message.setSubject("[Start Study] 이메일 인증번호");
    message.setText("인증번호는 [" + code + "] 입니다. 5분 이내에 입력해주세요.");

    try {
        mailSender.send(message);
    } catch (MailException e) {
        log.error("이메일 인증코드 발송 실패: {}", email, e);
    }
}
```

```java
// backend/src/main/java/com/study/studyproject/global/config/AsyncConfig.java
@Bean(name = "mailExecutor")
public Executor mailExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(10);
    executor.setQueueCapacity(50);
    executor.setThreadNamePrefix("mailExecutor-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}
```

- `EmailVerificationServiceImpl.sendCode()`는 쿨다운 락 획득 → 인증 코드 생성/저장(Redis) → `emailSender.send(...)` 호출까지만 처리하고, 실제 SMTP 전송은 `mailExecutor` 풀의 별도 스레드로 넘겨진다. 이 메서드는 `void`를 반환하므로 호출부는 전송 완료를 기다리지 않고 즉시 리턴한다.
- 결과적으로 API 응답 시간은 "Redis 락 획득 + 코드 저장" 정도로 짧아지고, SMTP 지연은 요청 처리 스레드가 아닌 메일 전용 풀 안에 격리된다. 메일 서버가 느리거나 일시적으로 장애가 나도 컨트롤러 스레드 풀 자체는 영향을 받지 않는다.
- 메일 전송용 스레드 풀을 **별도로** 둔 이유도 같은 맥락이다 — 애플리케이션 공용 스레드 풀(혹은 Tomcat 요청 스레드)과 분리해 두면, 메일 발송이 몰리거나 느려져도(`queueCapacity: 50`까지 대기) 다른 비동기 작업이나 요청 처리에 영향을 주지 않는다. 대기열(50)까지 가득 차면 `CallerRunsPolicy`에 따라 요청 스레드가 직접 메일 전송을 수행해, 작업이 조용히 버려지는 대신 처리 속도가 자연스럽게 느려지는 방식으로 백프레셔가 걸린다.
- 전송 실패는 `MailException`을 잡아 로그로만 남긴다(`sendCode()` 호출자에게 예외가 전파되지 않음) — 비동기 메서드의 예외는 호출 스레드로 되돌아가지 않으므로, 실패를 사용자에게 알리는 대신 재요청(쿨다운 만료 후 재발송)에 맡기는 구조다.
